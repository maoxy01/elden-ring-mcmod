# VFX 生产管线规范：审查修订版

## 当前有效契约（Codex 修订，2026-10-12）

下面的当前契约替代历史稿中的冲突结论。历史全文保留仅供追溯；改前备份在 `docs/code-backups/20261012-vfx-pipeline/`。

### 1. 范围与现状

- 当前底座已是纯原版战斗扩展，不再把 EF 迁移失败当成现状。
- 只修改视觉资源、渲染、预算校验和预览。伤害、命中空间、FP、技能动作、服务端推进不改。
- 黄金波动使用 `GoldenWaveEntity/GoldenWaveRenderer`，必须纳入管线；不能只检查 `SkillEffectEntity`。
- 武器保持用户确认的薄片像素、低饱和材质，小图集；不因这份规范恢复 2048 运行图集或重做玩家/Boss。

### 2. 预算口径

| 指标 | 当前口径 |
| --- | --- |
| 原生网格 | 每实体最多 96 box / 576 quad / **2304 提交顶点** |
| 贴片 | 水鸟最多 12，其余支持类型最多 6；每片 4 提交顶点 |
| 地表碎块 | 每实体最多 12，近距离全量、中距离最多 6、远距离 0；全局每帧最多 32 次原版方块模型绘制 |
| 自有通道每帧提交 | 合计最多 30000 顶点；网格优先，贴片使用剩余额度 |
| 并发压力 | 超过 40 个候选实体时降为简化主形状，不在服务端取消技能或删除判定实体 |
| 单玩家/单次施法上限 | 当前静态特效没有客户端 caster/cast 标识，**不能冒充已实现**；不得错误地按 Kind 分组替代施法实例 |

原版方块模型可能由资源包改成复杂模型，其实际顶点/RenderType 成本不能用 box 数乘 24 冒充实测。
30000 顶点上限约束两条自有通道，不含原版方块模型、场景及其它模组。
CPU 对象生成、顶点提交、GPU 可见面数、GPU 时间、屏幕 overdraw 是不同指标。
按帧提交，不能把 20Hz tick 当作渲染帧率。GPU 1.5/6ms、p99 33ms 仅是待测目标，不是兼容或性能保证。

### 3. 剔除与透明

- 保留两个静态自有 RenderType；原版碎块可能使用额外的原版 RenderType，不保证全场景只有两次切换。
- 半透明双面渲染有视觉意义，不承诺开启 cull 零损失或固定减半。
- 仅对接近完全不透明的封闭盒体，在 CPU 提交前跳过背向面；相机在盒内时保留各面。
- 半透明波面、刀光仍保留背面。预算按最坏六面计数；有效面数随相机和透明度变化。
- 无需新建每技能 RenderType，不在 `render()` 中创建 RenderType。

### 4. 配色与降级

- 配色资源：`assets/eldencombat/fx/palette.json`，按语义 ID 与明暗档引用。
- 客户端资源通过 F3+T/资源包重载；**不是服务端 `/reload`**。坏数据保留最后有效快照，并记录错误。
- 首轮保留原配色，避免技术接入擅自改变已确认的特效。基础武器旧金与施法黄金不必使用同一亮度。
- 0–16 格：完整主形状、贴片和最多 12 碎块；16–48 格：完整主形状/贴片，最多 6 碎块。
- 48–128 格：简化原生轮廓，不绘制贴片或碎块；超过 128 格：不绘制技能几何。
- 覆盖传入数据的实际实体跟踪/视锥范围；不保证服务器未同步的实体在任意距离可见。
- 近距离贴片仍是主要美术表现，同时保留淡原生轮廓。缺图集时回退原生网格。
- 光影导致贴片变暗不能可靠自动检测；在配色 JSON 加 `"slashSprites": false` 并 F3+T，可明确选择原生兜底。
- 命中确认仍由现有服务端结果与客户端反馈完成。不得从视觉重叠推导命中；声音、震动、闪色都受玩家设置和渲染环境影响，不称“绝不失效”。

### 5. 缓存与生命周期

普通视觉实体的盒体/贴片描述按客户端 tick 缓存；玩家与实体位移仍使用插值。黄金波面保留实际前沿插值，成型后缓存固定相对偏移。
缓存按实体弱引用存放，资源重载版本变化使缓存失效。未声称所有 CPU/GPU 分配均为零。
保留 `ownerEntityId / phase / progress` 的原有语义，`SkillEffectEntity` 寿命仍由原服务端控制，最大 40 tick。
地面波寿命遵从既有服务端运动契约，不为了渲染预算修改其伤害实体寿命。跟随型取消、切武器、死亡、离线、跨维度清理仍需独立服务端场景验收。

### 6. 导出门禁与证据

`exportSkillFx` 使用同一份 Java 生成函数；遍历所有 Kind、三个 phase、多种 radius/progress、黄金前沿 travel/blockedLanes，校验数量、有限值、尺寸、色板引用、结束帧为空。
导出 `art/skill-fx/budget-report.json`，区分自有网格顶点与原版碎块；8 个最大实体合计作为静态提交估计，不是八人实机性能结果。
预算检查属于 Gradle `check/build`，浏览器检查还会独立校验报告，失败时非零退出。
Sodium、Iris、Entity Culling、独立服务端的本轮场景验证字段默认 false。白名单、成功构建、单元测试、浏览器预览都不冒充游戏内兼容验收。

### 7. 不在本轮擅自扩张的内容

区域雾、建筑模块、音高曲线、新 Shader、强制色彩比例，以及没有消费者的元素/战技 JSON 不在本轮添加。
60/30/10 是构图建议，黄金波动和命定之死可按主题例外；不做“所有顶点必须属于 1/16 网格”检查来误伤运动插值和相机朝向贴片。

## 2. 预算表（这是本文件的核心，所有新特效先对照这个表）

### 2.1 几何预算

| 项                       | 上限                           | 依据                        |
| ----------------------- | ---------------------------- | ------------------------- |
| 单特效实体 quad              | **96 方块 × 6 = 576**（现状）      | 保持                        |
| 单特效实体有效渲染 quad          | **≤ 288**                    | 见 §4.1 背面剔除优化             |
| 单特效实体顶点                 | ≤ 1152                       | 576 × 2 tri × 4 顶点中共享后约此数 |
| 地表碎块                    | ≤ 12 / 次                     | 现状已约束，保持                  |
| 贴片 Sprite               | ≤ 12 / 战技（水鸟）、≤ 6（命定之死 / 咒血） | 现状已约束，保持                  |
| **每 tick 新生成顶点（单玩家）**   | **≤ 8000**                   | 见 §4.2，这是真正的 CPU 瓶颈       |
| **每 tick 新生成顶点（8 人同屏）** | **≤ 30000**                  | MC 是 CPU 密集，顶点生成在 Java 侧  |

### 2.2 并发预算（新增，目前完全空白）

| 层级          | 上限       | 说明                      |
| ----------- | -------- | ----------------------- |
| 单战技同时存活实体   | **≤ 4**  | 水鸟三段、授血追击叠层会自然逼近这个值     |
| 单玩家同屏实体     | **≤ 12** | 覆盖"取消旧技能立刻放新技能"的重叠期     |
| 全局同屏实体（8 人） | **≤ 40** | **超出后按 §5 分层降级，不按距离剔除** |

> 最后一条是刻意的：**按距离剔除会让远处队友的技能看起来"没放出来"，信息缺失比掉帧更糟。** 远距离降低密度，不取消。

### 2.3 叠加强度预算（新增）

| 项                                 | 上限                        |
| --------------------------------- | ------------------------- |
| Overdraw 层数                       | **≤ 4 层**                 |
| 同 RenderType 种类                   | **≤ 2**（网格 1 + 贴片 1），保持现状 |
| Entity render 的 RenderType 切换次数/帧 | ≤ 2                       |
| GPU 帧时间贡献（单战技）                    | ≤ 1.5 ms                  |
| GPU 帧时间贡献（8 人混战）                  | ≤ 6 ms                    |

### 2.4 生命周期预算

| 项        | 值                                                   |
| -------- | --------------------------------------------------- |
| 临时特效实体寿命 | ≤ 40 tick（现状，保持）                                    |
| 跟随型刀光    | 必须在 **取消 / 切武器 / 死亡 / 离线 / 跨维度** 五个时机全部结束（现状已覆盖，保持） |
| 已释放的静态冲击 | 允许跑到寿命结束再消失（现状已定，合理）                                |

## 3. 技术选型决策树

新做一个效果前，按这个顺序问：

```
1. 它是"体积/轮廓"还是"轨迹/条带"？
   ├─ 体积轮廓（冲击环、地面波面、立柱、法阵）
   │    └─ 能否用 ≤96 个方块拼出来？
   │        ├─ 能 → 【路线 A 立体网格】
   │        └─ 不能 → 拆成多个 ≤96 的实体，且总数进并发预算 §2.2
   └─ 轨迹条带（刀光、刃线、鞭痕）
        └─ 相机朝向贴片是否够用？
             ├─ 够 → 【路线 B 贴片】成本最低，优先选
             └─ 需要真实空间体积 → 【路线 A】，但要用细长方块表达

2. 它需要随时间生长/变形吗？
   ├─ 需要，且形状复杂 → 【路线 A】+ 关键帧插值（见 §4.2）
   └─ 只需淡入淡出/缩放 → 【路线 B】最省

3. 它需要精确命中空间吗？
   └─ 需要 → 必须路线 A。贴片是 billboard，无法表达深度，
        用它做"在某处的能量场"会穿模。
```

**判断准则一句话：贴片是二维欺骗，网格是真三维。需要空间真实感就用网格，否则用贴片。**

### 3.1 明确不要用原版粒子做主表现

`level.addParticle(...)` 禁止用于任何主表现通道。允许的场景只有两个：

| 允许                      | 禁止              |
| ----------------------- | --------------- |
| 飘散余烬、灰尘、飞溅碎片（数量少、非关键信息） | 技能主形状、传播波面、命中确认 |

理由在 `07_追忆武器技能表现规格.md` 已论证：粒子被玩家关掉是最常见的 MC 降级场景，而且原版粒子在 Iris 下会被光影包接管。

## 4. 三个真实风险与规避方案

### 4.1 【高】透明渲染默认不剔除背面，白白多画一半

现状描述是"正常透明混合、深度测试，不写入深度"。这条组合是对的（不写深度避免遮挡后续半透明），但 MC 的半透明 RenderType **默认关闭背面剔除**。

一个封闭方块 6 个面，实际朝向相机的只有 ≤3 个。关掉 cull 意味着每帧画 6 面。

**规避**：确认 `SkillEffectMesh` 生成、`SkillSlashSpriteRenderer` 使用的 RenderType 是否在 `.setCull(true)` 状态。对于明确封闭的方块体（地表碎块、立柱、悬浮方块）应当开启剔除。

> 收益：有效渲染 quad 从 576 降到 ≤288，直接减半，零视觉损失。  
> 例外：刀 Beam、波面这类"薄壳"，如果希望从背面也能看到，就保留不剔除——但那要进 §2.3 的 overdraw 计数。

**这条我建议作为第一个优化项**，因为它改动最小、收益最直接。

### 4.2 【高】每 tick 在 Java 里重算逐顶点位置是 CPU 陷阱

现在的表述是"接受 radius、归一化寿命进度和 phase，返回 Strip/网格"。如果这些数值是**每次渲染调用时实时计算生成**，那么在 20Hz × 多实体并发下：

```
8 实体 × 576 quad × 4 顶点 = 18432 次位置+颜色计算 / tick
× 20 tick/s = 368,640 次 / 秒
```

而且每帧新建顶点数据对象 → GC 压力。**MC 是 CPU 密集不是 GPU 密集**，这才是真正的瓶颈所在，不是填充率。

**规避（按优先级）**：

| 方案                        | 做法                                                            | 适用        |
| ------------------------- | ------------------------------------------------------------- | --------- |
| **① 拓扑缓存 + phase 关键帧插值**  | 网格拓扑（哪些方块、连接关系）只生成一次；每 tick 只按 progress 插值**少量控制点**，顶点位置由拓扑推导 | 波面、追踪型效果  |
| **② 顶点复用池**               | 预分配 `float[]` / `PoseStack` 缓冲，绝不每帧 new                       | 所有效果的最低要求 |
| **③ 把动画推进 RenderType 之外** | 一次性生成静态 mesh，用 PoseStack 的 scale / rotate / translate 做整体动效   | 整体缩放、旋转类  |

`SkillSlashSprites` 目前的设计（**不依赖 Minecraft 的纯函数，返回 Strip 描述**）其实已经很接近方案 ① 的形状——它返回的是数据描述不是顶点缓冲，只要渲染端把 strip → 顶点的转换做成**每 quad 即时写给 VertexConsumer**，就不产生中间对象。这条路是对的，别改成"先算出 List<Vertex> 再写"。

### 4.3 【中】借用原版 `explosion_0`–`_15` 的两个隐患

用原版粒子图集帧做贴片是个聪明做法（零新增资源），但有两个坑：

| 隐患                                   | 后果                                       | 规避                                                         |
| ------------------------------------ | ---------------------------------------- | ---------------------------------------------------------- |
| **玩家装了资源包改了粒子图集**                    | explosion 帧长得完全不一样，你的"银白刀光暗银边"变成别人画的任何东西 | 在项目文档里明确写：这是引用原版资产，**受资源包影响是预期行为，不算 bug**。若要锁定外观，切回路线 A 网格 |
| **particle shader 在 Iris + 光影下会被接管** | 你设的"全亮、深度测试、不写深度"可能被光影包的粒子处理改写，效果变暗或消失   | 见 §5 分层：贴片层属于"装饰层"，它失效时必须还有保底层                             |

**这不是要求你们换方案**——复用原版图集的收益远大于成本。只是要认识到：**路线 B 是唯一会在特定环境下静默失效的通道**，所以下一节的分层是必须做的，不能省。

## 5. 效果分层与降级（最关键的一节）

每个战技的表现必须拆成三层，分别预算、分别实现：

| 层       | 内容                            | 允许的实现手段                    | 允许失效？                     |
| ------- | ----------------------------- | -------------------------- | ------------------------- |
| **必须层** | **命中确认** —— 玩家必须知道"打中了 / 没打中" | 顿帧、音效、相机震动、受伤者的受击闪白、武器模型发光 | **绝不允许**                  |
| 增强层     | 技能主形状 —— 玩家据此辨识这是哪个技能         | 路线 A 网格                    | 否（但有降级形态）                 |
| 装饰层     | 刀光、飞溅、余烬、残留燃烧                 | 路线 B 贴片、少量粒子               | **允许**（资源包 / Iris / 粒子设置） |

**硬要求：任何战技在"装饰层完全失效"的最坏情况下，仍然可辨认、仍然能确认有没有打中。**

每个通道是否会失效：

| 通道             | 是否会失效 | 备注                                |
| -------------- | ----- | --------------------------------- |
| 顿帧（客户端渲染冻结）    | 否     | 服务端 tick 照常，见 §6.1                |
| 受影响实体的受击闪白     | 否     | MC 原生 hurt flash，无需额外实现           |
| 命中音效           | 否     | 音量归零才会失效，属于玩家主动选择                 |
| 相机震动           | 否     |                                   |
| 武器/受影响单位的模型发光层 | 否     | 渲染时给该次绘制强制满亮度，不写世界数据、不触发 chunk 重建 |
| UI 失衡条跳动       | 否     |                                   |
| 路线 A 网格        | 极低    | 只在极端资源包冲突下失效                      |
| 路线 B 贴片        | **中** | 资源包改图集 / Iris 接管 shader           |

### 5.1 距离 LOD（补缺失）

现在完全没有距离策略。建议三档，**降密度不取消**：

| 距离         | 网格             | 贴片   | 地表碎块 | 备注        |
| ---------- | -------------- | ---- | ---- | --------- |
| 0 – 16 格   | 全量             | 全量   | 12   | 玩家自己与近战范围 |
| 16 – 48 格  | 全量             | 允许全量 | 6    | 队友范围      |
| 48 – 128 格 | 删除装饰层 + 波面段数减半 | 删    | 0    | 只保留主轮廓    |
| > 128 格    | **仅保留命中确认层**   | 删    | 0    | 不渲染技能几何   |

> 128 格是 MC 的实体渲染距离上限附近，超过就没有讨论意义。

## 6. 两条工程纪律（破坏一次的代价很大）

### 6.1 顿帧必须是客户端渲染冻结，服务端 tick 照常

这点在 `06_前后摇压缩与节奏重算.md` 已论证，这里重申因为 VFX 最容易误伤它：

**不要在顿帧时暂停 `SkillEffectEntity` 的 tick**，否则会出现"服务端判定照常推进，视觉却停在半空"，在 20Hz 下立刻产生"我躲过了却被判中"。

正确做法：顿帧只作用于客户端插值/渲染的时间源，实体和服务端逻辑不受影响。

### 6.2 RenderType 必须静态注册一次

**禁止在 `render()` 里调用 `RenderType.create()`。** 每帧新建 RenderType = 每帧新建 RenderStateShard 与 buffer，这是 MC Mod 最常见的性能错误。

现有两条路线各一个 RenderType，注册清单：

| RenderType            | 用途      | 关键参数                                   |
| --------------------- | ------- | -------------------------------------- |
| `skillEffectMesh`     | 路线 A 网格 | 全亮、透明混合、深度测试、**不写深度**、见 §4.1 决定是否 cull |
| `particleAtlasSprite` | 路线 B 贴片 | 原版 particle shader、全亮、深度测试、不写深度        |

共 2 个，符合 §2.3 预算。**后续不要为了某个技能再开第三个**——宁可复用现有两个并靠顶点色区分。

---

## 7. 把预算校验塞进导出管线（这是能省最多返工的一步）

你们已有 `EffectPreviewExporter` + `art/skill-fx/meshes.js` + `check-preview.mjs` 这条链。**在它里面加一个 budget gate**：

```
EffectPreviewExporter 导出时，对每个 SkillEffectMesh.Kind × 每个 phase 采样：
  1. 统计 quad 数        → 超 §2.1 就报错
  2. 统计有效渲染面数    → 校验 §4.1 剔除是否生效
  3. 统计 bounding box   → 校验没有退化尺寸 / 无限坐标
  4. 统计为此需要的顶点生成操作数 → 进 §2.1 的每 tick 生成预算
  5. 输出 budget-report.json 与 meshes.js 同目录
check-preview.mjs 读取 budget-report.json，任一项超标 → 非零退出（CI 失败）
```

这样做到的效果是：**超标在合入之前就被拦下来，而不是等实机验收时才发现帧率掉了。**

配套在 `budget-report.json` 里登记每个 Kind 的实测值，形成一张活的预算台账——随时间推移，新效果加进来时能立刻知道还剩多少余量。

### 7.1 效果登记表（建议的 report schema）

```json
{
  "kind": "WATERFOWL",
  "phaseMax": 3,
  "perPhase": [
    { "phase": 0, "quads": 288, "culledQuads": 144,
      "vertices": 576, "genOps": 1180, "overdrawLayers": 2 }
  ],
  "concurrentEntities": 3,
  "lifeTicks": 40,
  "sprites": { "max": 12, "layer": "decorative" },
  "lodProfile": "DEFAULT",
  "verified": { "vanilla": false, "iris": false, "sodium": false, "entityCulling": false, "dedicatedServer": false }
}
```

`verified` 字段是刻意加的：**没验过的环境就不能标 true**，这能从源头上杜绝"预览通过 = 验收通过"的误判（项目文档里已经两次强调了这一点，把它固化成数据字段比写在文档里有效）。

## 8. 验收清单

### 8.1 可机检（已有 43 项测试，补这几项）

| # | 检查                               | 状态                       |
| - | -------------------------------- | ------------------------ |
| 1 | 所有 Kind 的 quad / 顶点 / 生成操作数在预算内  | ❌ **待加**（§7 budget gate） |
| 2 | 封闭几何体的背面剔除已生效（渲染面 ≤ 生成面的一半）      | ❌ **待加**                 |
| 3 | 生命周期 ≤ 40 tick，且跟随型在 5 个取消时机全部结束 | ✅ 已有                     |
| 4 | cancel / 切武器 / 死亡 / 跨维度后无残留实体    | 需确认                      |
| 5 | 8 实体并发时顶点生成量在 30000/tick 内       | ❌ **待加**                 |
| 6 | 预览导出脚本无 NaN / 无限坐标 / 退化尺寸        | ✅ 已有                     |

### 8.2 必须人跑（Gradle 退出码不能替代）

三件事现在完全没做，而且都是质变风险的来源：

| 环境                        | 要验证什么                                      | 当前状态            |
| ------------------------- | ------------------------------------------ | --------------- |
| **Sodium 0.6.13**         | 批次渲染是否被 Sodium 改写；尤其是自己在 PoseStack 里做的每帧矩阵 | ❌ **未验证**       |
| **Iris 1.8.12**           | 路线 B 的粒子 shader 是否被光影接管；全亮是否还生效            | ❌ **未验证（最高风险）** |
| **Entity Culling 1.11.3** | **会不会把 SkillEffectEntity 当成普通实体剔除掉**       | ❌ **未验证（潜在致命）** |

**第三条是我最担心的**：Entity Culling 的原理是按视锥/遮挡剔除实体渲染。你的特效实体如果不在正常的实体渲染路径里、或者缺少正确的 culling box，可能被整批剔掉，表现为"技能放出来什么都看不见"，而且只在装了这个 Mod 时出现。

> 建议顺序：**Entity Culling → Iris → Sodium**。第一条是"有没有"，后两条是"好不好看"。

### 8.3 帧率基准（现在完全没有）

需要一个可重复的场景定义，不要各跑各的：

```
场景：超平坦世界，8 名玩家分散在 32×32 区域内，同时释放 8 个不同战技
采样：连续 30 秒，记录 avg / p1 / p99 帧时间
基线：先跑一次「不放技能」的同样场景做对照
目标：p99 帧时间 ≤ 33 ms（30 FPS 底线），技能期间相对基线增幅 ≤ 6 ms
```

## 9. 执行顺序

```
① §4.1 背面剔除            ← 改动最小，quad 直接减半，先拿这个收益
② §7 budget gate 塞进导出   ← 越早越好，之后每加一个效果都在护栏内
③ §8.2 Entity Culling       ← 最高风险的未验证项，可能直接"什么都看不见"
④ §8.2 Iris                 ← 路线 B 唯一会静默失效的通道
⑤ §5.1 距离 LOD             ← 多人下才显出价值，可稍后
⑥ §8.3 帧率基准             ← 需要 8 人环境，最后做
⑦ §5 分层和降级表补全        ← 随每个新技能填写，持续进行
```

## 10. 一句话

> 你们已经把最难的部分做完了——**不依赖粒子、不依赖第三方、预览可离线跑**。剩下的不是"怎么做出更好看的效果"，而是**建立护栏**：让每一个新加进来的效果在写出来的那一刻就知道它有没有超预算，以及它在哪些环境下会失效。

技美的价值在这里不是再画一个效果，而是让第 100 个效果和第 8 个效果一样可控。
